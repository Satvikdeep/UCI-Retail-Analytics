# Decision log

| Decision | Evidence and alternatives | Rationale and validation |
|---|---|---|
| PostgreSQL with an isolated project cluster | PostgreSQL 14.19 tools were already installed. Considered an existing service or DuckDB. | Preserved PostgreSQL implementation and used an owner-only Unix socket with TCP disabled. The rebuild starts and stops only the project cluster when needed. |
| Pin the original workbook and extract standard-library OOXML | The UCI 502 archive contains the expected two-sheet workbook. General spreadsheet readers may coerce identifiers and Excel prices to floats. | Stream the original XML, keep the date serial and decimal price, verify headers, dates, file hash and 1,067,371 rows. No Python dependency installation is needed for rebuild. |
| Correct the initial retain-all baseline for a verified mirrored block | Initial profiling retained all rows, then found the same daily totals and 1,088 invoice IDs across the sheets. Exact full-field multiset comparison matched all 22,523 overlap rows. Within-sheet repeats remain ambiguous. | Keep the later sheet’s entire overlap. Retain 11,812 other exact-looking excess rows in baseline. The corrected positive total is £19,699,784.97 versus £20,108,995.40 with mirrored merchandise included. Jan–Nov comparisons are outside the overlap. SQL and Python verified multiplicity. |
| Separate catalogue and special-code classes | Descriptions identify postage, fees and adjustments. Some nonnumeric codes resemble real products. A simple sign or invoice-prefix filter includes material fees. | Main analysis uses a conservative catalogue code pattern plus observed exclusions, with possible catalogue visible. Compare broader product codes, all priced codes, collapsed repeats and extreme-line removal. |
| Preserve raw value and normalize analytical price to 0.001 GBP | Some source prices contain floating-point serialization residue. Eighteen source records have three meaningful decimal places. | Store original and normalized numeric amounts. Validate unit normalization against tolerance; disclose the aggregate precision bridge. Use a different calculation in Python with integer millipounds. |
| Use invoice ID with earliest timestamp at invoice grain | Invoice IDs recur by product and some have multiple times. The consistency profile finds zero cross-date, cross-customer or cross-country IDs. | Aggregate invoice values once. Use line time for cancellation matching. The population and amounts reconcile at every exported period and market key. |
| Compare Jan–Nov and require volume plus ID coverage for named-market comparisons | The workbook ends on December 9, 2011. Small markets can have very high percentage changes. | Compare equal calendar months. Retain every country in the selector, show UK separately and require pooled £100k, 30 invoices and 80% ID coverage in each period for the named benchmark. |
| Decompose change into invoice volume and average invoice value | Known order counts and invoice value can explain the arithmetic change. Separating price from product and buyer mix would require stronger assumptions. | Use a symmetric two-factor bridge, then isolate anonymous activity and changes outside a fixed top-five account set. Verify both bridges and retain the near-flat UK result. |
| Use exact-key latest-first allocation and two windows | Source fields contain no original-order reference. Candidate purchases can repeat and observed order quantities are finite. Considered simple nearest-row joins and omitting linkage. | Use only strictly earlier sales, cap consumption and report ambiguity and unmatched balances. Show 90-day baseline and 365-day sensitivity. Sales reconciliation is independent of the inferred allocations. |
| Focus customer risk on observed repeat and concentration | Identification is incomplete and the dataset ends on a fixed day. RFM would add segmentation assumptions without a distinct management action. | Show top shares alongside coverage, equal-age repeat cohorts and small denominators. Use first observed, no churn or lifetime-value label. |
| Use a static local report and dashboard | The SQL produces ready-to-use aggregate CSVs. A service or live database connection would add dependencies for reviewers. | Generate a payload from the same CSVs, enable browser-only filters with documented scope and keep data read-only. The optional browser QA uses the installed Chrome and a project-scoped Playwright package. |
